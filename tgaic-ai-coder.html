TGAIC References — Architecture & Terminology

This reference explains the pieces behind TGAIC and the terminology you will encounter while selecting and running local AI models.

TGAIC HTML: the user interface. It owns the visible conversation history and sends requests to the local bridge.

PowerShell bridge: the browser-facing local HTTP layer. It supplies CORS headers, proxies requests, exposes model-management helpers, and performs Hugging Face discovery.

llama-server: the server executable supplied by llama.cpp. It loads compatible models and performs inference.

GGUF model: the actual trained model data used for inference: weights, tokenizer information, and metadata packaged for llama.cpp.

2. What is the AI model?

The model is the trained neural network that produces the answer. It contains learned numerical weights created during training. TGAIC itself does not contain that intelligence; it provides the interface and plumbing used to communicate with the model.

Examples of model families include Qwen, Llama, Gemma, Mistral, DeepSeek-derived models, and many community fine-tunes. A Hugging Face repository may contain several sizes or quantizations of the same underlying model.

Base model: primarily trained to continue text. Instruct/Chat model: additionally tuned to follow prompts and respond conversationally. Coder model: trained or fine-tuned with additional emphasis on source code and software tasks. Instruct/chat or coder-instruct models are normally the most useful choices for TGAIC.

3. Llama vs llama.cpp vs llama-server

The similar names are confusing, but these are different things:

  • Llama — a family of AI models released by Meta. A Llama GGUF is one possible model TGAIC can run.
  • llama.cpp — an open-source C/C++ inference runtime. It is not an AI model. It can run many supported model families, not just Llama.
  • llama-server — a server executable included with llama.cpp. TGAIC uses it to expose the locally loaded model through HTTP/OpenAI-compatible endpoints.

In the current TGAIC architecture, llama.cpp/llama-server is the engine and the GGUF file is the model.

4. GGUF and quantization

GGUF is the model file format used by llama.cpp. It packages model tensors together with metadata and tokenizer information so the runtime can load the model.

Quantization stores model weights at reduced numerical precision. This makes a model smaller and reduces memory requirements, usually with some trade-off in model quality.

  • Q8 — relatively high precision and larger memory/file requirements.
  • Q5 / Q6 — middle ground between size and retained precision.
  • Q4_K_M — a common practical balance of size, quality, and local hardware requirements.
  • Q3 / Q2 — progressively smaller, but with greater potential quality loss.

Quantization and parameter count are separate concepts. A 7B Q4 model and a 3B Q4 model can have the same quantization family while still being very different in size and capability.

5. Hugging Face and the Hugging Face Hub API

Hugging Face is an online ecosystem for hosting and sharing models, datasets, model cards, and related files. TGAIC uses Hugging Face primarily as a catalog for discovering GGUF repositories.

The Hugging Face Hub API is the programmatic interface used by the TGAIC bridge for model discovery. The bridge can search repository metadata and inspect repository files without scraping a normal web search-results page.

A model repository can contain the model card/documentation, multiple GGUF quantizations, configuration information, and optional companion files such as multimodal projectors.

6. Inference, tokens, and tokenization

Inference means running an already-trained model to generate an answer. Training creates or changes model weights; inference uses those existing weights.

Models process tokens, not words exactly as they appear on screen. A tokenizer converts text into token IDs. A token may represent a whole word, part of a word, punctuation, whitespace, or another text unit.

Generation is iterative: the model predicts a next token, that token becomes part of the active context, and the process repeats.

7. Context window, KV cache, and generation

Context window: the active token capacity the model/runtime can consider at one time. It includes system instructions, conversation history, the current prompt, and generated tokens.

Local RAG in TGAIC: reference files are tokenized by the currently loaded llama.cpp model through /tokenize. The bridge breaks the files into overlapping token-sized chunks and persists the local index under the current Windows user's local application-data area. For each question, the bridge retrieves matching chunks within the RAG token budget; TGAIC adds those chunks to the model request with filename and line-range provenance. RAG does not retrain or permanently modify the model.

Prompt tokens: tokens supplied to the model. Completion tokens: tokens generated by the model.

KV cache: runtime memory that preserves attention state for the active context. Increasing context length can therefore increase memory usage even when the GGUF file itself has not changed.

Temperature: a generation setting that influences randomness. Lower values generally make generation more deterministic; higher values allow more variation.

Sampling: the strategy used to select the next token from the model's probability distribution.

The important distinction is that the reference material is retrieved at question time. The GGUF model is not retrained, fine-tuned, or permanently changed by indexing files.

9. Why TGAIC tokenizes references with the selected model

Different model families can use different tokenizers, so the same source file does not necessarily produce the same token count with every model. TGAIC therefore asks llama-server /tokenize to tokenize the reference text using the model selected in TGAIC.

This makes the chunk target, overlap, and RAG budget correspond to the token units the runtime actually uses rather than estimating tokens from characters or words. In llama-server router mode, the model name must be included in the /tokenize request so the router knows which model/tokenizer should handle it.

Chunk target: desired maximum size of each reference chunk. Chunk overlap: repeated tokens between adjacent chunks so a useful idea or code block near a boundary is less likely to be split apart. RAG budget: maximum retrieved-reference tokens TGAIC will try to add to one question. Maximum chunks: an additional cap on how many retrieved chunks can be injected.

If you switch to a materially different model/tokenizer, rebuilding the index is the cleanest way to make the stored chunk boundaries and token counts match that model. Reopening the page alone does not require rebuilding: the bridge reloads the persisted index and its indexed-file manifest.

10. Retrieval in the current TGAIC implementation

The current TGAIC RAG implementation is token-aware lexical/code retrieval. The bridge stores token-sized chunks and scores them against the question using textual/code signals such as identifiers, terms, occurrences, filenames, and exact matches. It then selects the strongest chunks that fit within the configured token budget.

This works particularly well for coding references where questions often contain exact artifacts such as Java class names, PL/SQL package names, table names, columns, methods, parameters, error codes, filenames, and other identifiers.

Current RAG metadata includes source filename and approximate line range so retrieved evidence can be identified in the prompt and cited by the coding model. The persisted index is stored locally under %LOCALAPPDATA%\TGAIC\rag-index.json. The browser distinguishes newly selected STAGED references from bridge-persisted INDEXED references.

11. Embeddings and semantic RAG — what they are and where they fit

An embedding is a vector: a list of numbers representing the semantic meaning of text. With embedding-based RAG, each reference chunk is converted into a vector and the user's question is converted into a vector using the same embedding model. A similarity calculation, commonly cosine similarity, can then find chunks whose meanings are close even when they do not share the same literal words.

Tokenizer and embedding are not the same operation. Tokenization converts text into discrete token IDs used by a model. Embedding converts content into a numerical vector designed for similarity comparisons.

TGAIC's current RAG does not yet build embedding vectors; it uses lexical/code-aware retrieval. llama-server does support embedding endpoints such as /v1/embeddings when an appropriate embedding model is loaded, so a future TGAIC version can add semantic or hybrid retrieval without requiring an external cloud service.

12. Reranking and hybrid retrieval

A more advanced RAG pipeline can combine multiple retrieval stages. Fast lexical and/or embedding search first produces candidate chunks. A separate reranker model can then read the question and those candidates and reorder them by relevance before the final chunks are sent to the coding model.

question
   │
   ├── lexical search ─────┐
   └── embedding search ───┤
                           ▼
                     candidate chunks
                           │
                           ▼
                    optional reranker
                           │
                           ▼
                  best evidence chunks
                           │
                           ▼
                     coding model

llama-server exposes reranking support when a suitable reranker model is loaded. This is a possible future TGAIC evolution. It is not required for the current local lexical RAG pipeline.

13. RAG, context windows, and why retrieval matters

A model has a finite context window. Sending every source file with every question wastes context, increases prompt-processing time, and can crowd out conversation history or answer space. RAG is useful because it tries to send only the small portion of the reference library that appears relevant to the current question.

The effective prompt can contain system instructions + conversation history + your question + retrieved RAG chunks + room for the generated answer. The configured RAG budget therefore should be comfortably smaller than the model/runtime context size.

For example, with an 8192-token context, a 4000-token RAG budget is a ceiling for retrieved evidence, not a promise that every request should consume 4000 RAG tokens. TGAIC retrieves fewer chunks when fewer are relevant.

14. Retrieval diagnostics and source transparency

TGAIC exposes the exact chunks used for a RAG-assisted answer. The expandable RAG Sources Used panel shows filename, approximate line range, token count, retrieval score, selection reasons, and the actual chunk text supplied to the coding model.

This separates retrieval quality from generation quality: a bad answer can be diagnosed by checking whether the right evidence was retrieved first.

15. Exact-file and code-aware lexical ranking

Current retrieval first gives a strong boost to an exact indexed filename named in the question. It then ranks chunks using normal terms, identifiers, filenames, exact text, and generic code-oriented structural signals such as import, package, SQL keywords, JDBC/connection types, parameters, exceptions, and declarations.

This is still lexical/token-aware RAG rather than semantic embedding RAG, but it improves precision for source-code questions without requiring another model.

16. GPU VRAM, system RAM, model size, and offload

A GGUF model does not always need to fit completely inside GPU VRAM. llama.cpp can place some model layers/work on the GPU and leave the remainder in system RAM for CPU processing.

  • GPU VRAM: fast memory attached to the GPU. More VRAM generally allows more model work to remain on the GPU.
  • System RAM: can hold model data that does not fit in VRAM, allowing models larger than the GPU's memory to run.
  • GGUF file size: a useful sizing signal, but it is not identical to total runtime memory consumption.
  • GPU offload: assigning selected model layers or computation to the GPU while other portions remain CPU/system-memory based.
  • Runtime overhead: context/KV cache, working buffers, the operating system, and other processes also consume memory.

This is why a machine with 2 GB of VRAM can sometimes run a GGUF larger than 2 GB. It may simply be using a mixture of GPU VRAM, system RAM, and CPU inference. Whether it is fast enough is a separate question.

TGAIC's model-size filter is therefore a discovery aid, not a guarantee that a model will load, fit comfortably, or perform well on a particular computer.

17. Additional terminology

LLM: Large Language Model — a neural network trained to model and generate sequences of tokens.

Parameters: learned numerical values inside a model. Names such as 3B, 7B, or 14B roughly indicate billions of parameters.

Weights: the learned parameter values stored in the model.

Training: the process that adjusts model weights from data. Normal TGAIC chat does not train the model.

Fine-tune: additional training used to specialize an existing model for a domain, task, or behavior.

LoRA: a parameter-efficient adapter technique that can modify model behavior without retraining/replacing every base-model weight.

Prompt: the input and instructions sent to the model.

Embedding: a numerical vector representation of content, often used for similarity search and retrieval.

RAG: Retrieval-Augmented Generation — retrieving relevant reference material and adding it to the model context before generation.

Multimodal: a model that can work with more than text, such as images. Some llama.cpp multimodal models use an mmproj companion file.

API: Application Programming Interface. TGAIC communicates through HTTP APIs between the browser, bridge, and llama-server.

CORS: browser cross-origin security rules. The TGAIC bridge supplies the browser-facing CORS headers needed by the local HTML UI.

TGAIC Help — Local Setup

Current companion bridge: tgaic-ai-coder-bridge-v0031.ps1. The HTML and bridge are separate files; use the current bridge when running this page.

Run the downloaded HTML locally: the GitHub Pages copy is not the normal TGAIC runtime. Because GitHub Pages is HTTPS and the TGAIC bridge is normally plain HTTP on 127.0.0.1:8787, modern browser mixed-content/private-network rules may block the hosted page from reaching the bridge. Download tgaic-ai-coder.html, then double-click the local file.

Architecture. TGAIC uses a single-file browser UI, but the complete local runtime also requires the PowerShell bridge and llama.cpp. TGAIC is therefore local-first and dependency-light, but unlike TGG Grid it is not a browser-only Single-File Local Application. TGAIC is the HTML conversation UI. The PowerShell bridge listens on 127.0.0.1:8787 and provides the browser-safe API/CORS boundary. llama-server listens on 127.0.0.1:8080, loads the GGUF model, and performs inference. Keep both console windows open while chatting.

1. Install llama.cpp. Open Command Prompt and run:

winget install llama.cpp

Winget may report that PATH was modified. If so, close that Command Prompt and open a new one. Verify the installation:

llama-server --version
where llama-server

2. Start a model with llama-server. The easiest method is -hf, which lets llama.cpp obtain a compatible GGUF model from Hugging Face. Our known-working laptop example is:

llama-server -hf Qwen/Qwen2.5-Coder-1.5B-Instruct-GGUF:Q4_K_M --host 127.0.0.1 --port 8080 -c 4096

The first launch downloads/caches the model. Wait until the console reports model loaded and listening on http://127.0.0.1:8080. Leave this window running.

3. Alternative: run a GGUF file you already downloaded.

llama-server -m "C:\Models\your-model.gguf" --host 127.0.0.1 --port 8080 -c 4096

-hf is convenient for downloading/running a Hugging Face GGUF repository; -m is useful when you want explicit control over a local GGUF file.

4. Start the TGAIC PowerShell bridge. Put the bridge PS1 somewhere convenient, open a second Command Prompt in that directory, and run:

powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tgaic-ai-coder-bridge-v0031.ps1

The bridge should report Listening : http://127.0.0.1:8787/ and Upstream : http://127.0.0.1:8080/v1. Leave this second console window running.

5. Download and open TGAIC locally. Download or clone the repository so you have a local copy of tgaic-ai-coder.html, then double-click that file. TGAIC is intentionally run directly from disk as a file:// application. Do not rely on the GitHub Pages-hosted copy for normal bridge access. The endpoint should remain:

http://127.0.0.1:8787/v1

Leave the Model field blank and click Connect. TGAIC first checks the bridge and then requests /v1/models; the loaded llama.cpp model should be discovered automatically. A green Connected · 1 model badge means the entire chain is working.

6. Chat. Type a prompt and press Enter to send. Use Shift+Enter for a new line. Stop aborts the current generation. Disconnect disconnects the HTML UI but leaves the bridge and llama.cpp running. Stop Bridge asks the PowerShell bridge to exit; llama.cpp continues running separately.

7. Shut everything down. Use Stop Bridge or press Ctrl+C in the bridge console. Then press Ctrl+C in the llama-server console to unload the model and stop the inference server. Closing the HTML page does not automatically stop either process.

8. Start again later. You do not normally need to reinstall llama.cpp or redownload an already cached model. Start llama-server with the desired model, start the bridge, double-click TGAIC, and click Connect.

Useful checks.

llama-server --version

curl http://127.0.0.1:8080/health

curl http://127.0.0.1:8080/v1/models

curl http://127.0.0.1:8787/health

curl http://127.0.0.1:8787/v1/models

Troubleshooting. If TGAIC says the bridge is unavailable, confirm the PowerShell bridge is running on port 8787. If the bridge is ready but the model request fails, confirm llama-server is still running on port 8080. If llama-server is not recognized immediately after installation, open a new Command Prompt so the updated PATH is loaded. If the browser reports CORS errors, use the current TGAIC bridge; it owns the browser-facing CORS headers and deliberately does not pass conflicting llama.cpp CORS headers through.

Model notes. llama.cpp runs models in GGUF format. Hugging Face hosts many llama.cpp-compatible GGUF repositories. With -hf user/repository:quant, the quantization suffix selects a variant such as Q4_K_M. Smaller parameter counts and stronger quantization generally reduce memory requirements; larger models generally require more RAM/VRAM and take longer to generate. Hardware determines which model size is practical.

9. Standard TGAIC model-cache setup. We use llama.cpp's cache as the normal TGAIC model library and explicitly place it under C:\Models. In each new Command Prompt that will run llama.cpp, set:

set LLAMA_CACHE=C:\Models

This environment variable applies to that Command Prompt and processes launched from it. Models downloaded with -hf while it is set are cached under C:\Models and do not need to be downloaded again.

10. Download/add a model to the TGAIC cache. Stop router mode first with Ctrl+C, keep LLAMA_CACHE=C:\Models set, and launch the desired Hugging Face GGUF model once. Examples:

REM Known-working 1.5B baseline
llama-server -hf Qwen/Qwen2.5-Coder-1.5B-Instruct-GGUF:Q4_K_M

REM Better 3B model tested successfully on this laptop
llama-server -hf Qwen/Qwen2.5-Coder-3B-Instruct-GGUF:Q4_K_M

Wait for the download to reach 100% and for llama.cpp to report model loaded. The model is now cached. Press Ctrl+C; you do not need to use that -hf command again unless you deliberately remove the cached model.

11. Restart llama.cpp in TGAIC router mode. After adding models, return to the normal TGAIC server command:

set LLAMA_CACHE=C:\Models
llama-server --host 127.0.0.1 --port 8080 -c 8192

Notice that this command contains no -hf and no -m. That is intentional. llama.cpp is now acting as the model router instead of immediately loading one specific model. Start the bridge, open TGAIC, and click Refresh Models. The cached models should appear in the Local Model Manager and can be loaded from the page.

12. What we verified. We downloaded Qwen2.5-Coder 1.5B and 3B Q4_K_M models with LLAMA_CACHE=C:\Models, then confirmed both appear after restarting llama-server in generic router mode. We also successfully ran a roughly 3.4 GB / 6B-class GGUF on a machine with only 2 GB of GPU VRAM. That is an important practical result: a GGUF does not have to fit entirely in VRAM. llama.cpp can place some work on the GPU and use system RAM/CPU for the remainder. Performance still depends on the model, quantization, context size, total system RAM, memory bandwidth, and how much can be offloaded. The repeatable workflow remains: download/cache once → restart router → Refresh Models → Load Selected → chat.

13. Cache versus --models-dir. These are related but different. LLAMA_CACHE=C:\Models tells llama.cpp where its managed/downloaded cache lives. --models-dir "C:\SomeFolder" is useful when you already have manually managed GGUF files in a directory and want the router to discover them. For the normal TGAIC workflow, use LLAMA_CACHE=C:\Models. You can still add --models-dir later for a separate collection of manually downloaded GGUF files.

14. Where to find models online. There is no small fixed "full list" built into llama.cpp. Hugging Face is the primary catalog and contains a very large, changing collection of GGUF models. Use these references:

  • Hugging Face — all models filtered to the GGUF library ↗ — the broad catalog. Search within it for terms such as coder, Qwen, Gemma, or a parameter size.
  • Hugging Face — GGUF model search ↗ — another convenient browse/search view.
  • llama.cpp — Obtaining and quantizing models ↗ — official llama.cpp model documentation, including the -hf user/model[:quant] syntax.
  • Qwen2.5-Coder 3B Instruct GGUF ↗ — the 3B coder model now tested on this laptop.
  • Qwen2.5-Coder 7B Instruct GGUF ↗ — a substantially larger next step for stronger hardware.

15. Reading a Hugging Face GGUF model page. Prefer an Instruct or chat-tuned model for TGAIC rather than a base/pretraining model. Confirm that the repository contains GGUF files and is compatible with llama.cpp. Model repositories commonly provide multiple quantizations. Q4_K_M is a useful starting point because it balances model size and quality. Higher-bit quantizations such as Q5/Q6/Q8 generally require more memory/disk but preserve more model information.

16. Model size versus VRAM. Parameter count, GGUF file size, VRAM, and total system RAM are related but they are not the same limit. A model larger than available VRAM can still run because llama.cpp can split/offload work across GPU and CPU/system RAM. On the current 2 GB-VRAM test laptop, 1.5B and 3B models are proven, and a roughly 3.4 GB 6B-class coder/reasoning GGUF also runs acceptably. Treat the browser's file-size buckets as discovery aids rather than hard hardware limits. Larger models may load but become slower, consume more system RAM, or require a smaller context.

18. Important model-selection rule. Do not assume every model shown on Hugging Face is suitable merely because it contains a GGUF. Check parameter count, quantization/file size, model architecture/support, total RAM/VRAM, and whether the repository contains companion files. Some multimodal models use an mmproj companion; other repositories may include optional MTP/NextN-style sidecars. A download completing successfully does not prove that the exact GGUF conversion can be loaded by the installed llama.cpp build. TGAIC therefore treats compatibility as advisory and defaults the Hugging Face browser to Text GGUF only.

19. Hugging Face Model Browser. The online discovery panel searches GGUF repositories through the bridge. Enter a search such as coder, Qwen, or Gemma. Search criteria do not contact Hugging Face until you click Search Models. Page filling is handled by the bridge: it continues through Hub results until it has enough matching repositories for the requested TGAIC page or the Hub search is exhausted. Sort choices are only those supported by the Hugging Face model API, so sorting applies to the global Hub traversal rather than merely reordering one local page. The bridge also detects mmproj/MTP companion files and adds a compatibility hint. Use Copy -hf to copy the standard cache command plus the generated llama-server -hf user/repository:quant command. Downloading remains intentionally manual: stop router mode, paste/run the command, wait for the model to cache/load, stop that model with Ctrl+C, restart generic router mode, then use Refresh Models.

Current recommended routine: use the Hugging Face GGUF catalog to discover a model → copy its user/repository:quant identifier → set LLAMA_CACHE=C:\Models → run it once with llama-server -hf ... to download/cache it → Ctrl+C → restart the generic router → Refresh Models in TGAIC → Load Selected.

20. Hugging Face authentication, rate limits, and efficient search

Hugging Face allows anonymous API access, but larger or repeated searches can be rate limited. TGAIC supports optional authenticated requests in two ways.

Option A — HTML token field: enter an Hugging Face access token in the HF Token field in the model browser. The page sends it only to http://127.0.0.1:8787 in the X-HF-Token header. The bridge converts it to a Hugging Face Bearer token. TGAIC does not save this value to localStorage, sessionStorage, cookies, or a file; reloading or closing the page clears it.

Option B — environment variable:

set HF_TOKEN=hf_your_token_here
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tgaic-ai-coder-bridge-v0031.ps1

If both are present, the token entered in the HTML page takes precedence for that request. The bridge never prints the token itself.

API efficiency: the Hugging Face search response already includes model tags. The bridge first keeps only results tagged gguf (or clearly named as GGUF) and only then requests repository trees to discover exact GGUF filenames and sizes. This avoids a tree API call for every arbitrary model returned by the search.

Pagination: Results per page defaults to 10 and can be set from 1 to 100. A TGAIC page is result-oriented rather than tied one-for-one to a Hugging Face API page: the bridge follows as many Hub pages as necessary to collect the requested number of matching GGUF repositories, stopping early only when Hugging Face has no more results. The continuation cursor also remembers an offset within a Hub page so matches are not skipped between TGAIC pages.

21. Model compatibility and failed loads

A completed Hugging Face download and a valid .gguf filename are not a guarantee that the model will load. We encountered a Qwen3.5-derived GGUF that downloaded successfully but failed during llama.cpp tensor validation with a missing-tensor error. That type of failure happens after download and is distinct from cache/network problems.

TGAIC's compatibility column is therefore a pre-download hint, not a certification. It can identify obvious text versus multimodal repositories and companion files, and it can flag newer architecture families for extra caution, but the definitive compatibility test is still whether the installed llama.cpp build loads the exact GGUF conversion.

On Windows, llama.cpp may print failed to create symlink: A required privilege is not held by the client followed by switching to degraded mode. If the process continues afterward, that warning by itself is not the fatal model-load error; inspect the later llama.cpp messages for the actual failure.

22. Markdown responses

Assistant output is rendered as safe Markdown in the browser. Common headings, bold/italic text, numbered and bulleted lists, inline code, fenced code blocks, blockquotes, links, horizontal rules, and basic Markdown tables are supported. Fenced code blocks include a language label and Copy button. Model-produced HTML is escaped rather than trusted/executed.

23. Hosted page and browser security

The TGAIC repository may be viewed through GitHub Pages, but the supported runtime is the downloaded standalone HTML file. GitHub Pages uses https:// while the local TGAIC bridge normally uses http://127.0.0.1:8787. Modern browsers may restrict or block that HTTPS-to-local-HTTP request because of mixed-content, private-network-access, or enterprise security policies.

For reliable operation, download tgaic-ai-coder.html and open it directly from disk. TGAIC does not attempt to bypass browser security policies.

24. Internet access and tool boundaries

The local GGUF model itself does not browse the web, scrape sites, or search the Internet. Current chat inference is local. The Hugging Face Model Browser is a specific bridge feature that performs Hub API requests only when you initiate a model search. General web search, arbitrary URL fetching, autonomous browsing, and image generation are not currently part of TGAIC. Local reference-file RAG is now included: llama-server performs tokenization while the PowerShell bridge coordinates chunking, persistence, and retrieval.

25. Local Knowledge / RAG workflow

TGAIC includes a bridge-managed local Retrieval-Augmented Generation workspace. Expand Local Knowledge / RAG, choose Add Files or Add Folder, select a loaded model, and click Build / Rebuild Index. The selected files are STAGED until the build completes; files already present in the bridge's persisted index are shown as INDEXED.

During indexing, the bridge calls the selected model's /tokenize endpoint through llama-server. The returned token pieces are divided into overlapping chunks. The index is persisted under %LOCALAPPDATA%\TGAIC\rag-index.json, so closing/reopening the HTML does not by itself require a rebuild. The bridge reloads the index and returns the persisted file manifest to the page.

Rebuild when: reference files changed, files should be added/removed, chunk/overlap settings changed, or you want the index tokenized/chunked for a different model/tokenizer. Do not rebuild merely because: the HTML page was closed/reopened or the bridge was restarted and successfully reloaded the persisted index.

26. RAG settings and retrieval behavior

Defaults are approximately 800-token chunks, 150-token overlap, 4000-token retrieval budget, and 8 maximum chunks. Overlap protects useful code/context that crosses a chunk boundary. The retrieval budget limits how much reference evidence can consume the model's finite context window.

For each chat question, the bridge scores indexed chunks using lexical/code-aware signals and selects the strongest matches that fit the budget. TGAIC then injects those chunks into the request with source filename and line-range provenance. If no chunk matches strongly enough, chat continues without RAG context and the UI reports that condition.

This is retrieval and grounding, not training. Indexing reference files does not modify the GGUF model's learned weights.

27. Tokenization, embeddings, and future semantic retrieval

Tokenization and embedding solve different problems. Tokenization converts source text into the selected model's token IDs/pieces so TGAIC can make model-accurate chunk sizes and budgets. Embeddings convert chunks/questions into semantic vectors used for similarity search.

The current TGAIC RAG uses model tokenization plus lexical/code-aware retrieval; it does not currently create embedding vectors. A future semantic or hybrid RAG mode can use a dedicated embedding model through llama-server's embedding API, compare the question vector to stored chunk vectors, and optionally use a reranker model before sending the best chunks to the coding model.

Current:
files → selected model /tokenize → chunks → lexical/code retrieval → coder model

Possible future hybrid:
files → chunking → embedding model → vectors
question → embedding model → query vector
vectors + lexical matches → optional reranker → coder model

28. Router-mode RAG model requirement

When llama-server is running in generic router mode, POST requests such as /tokenize must identify the target model. TGAIC sends the currently selected model name automatically during RAG indexing and retrieval tokenization. This is why a model must be selected/loaded before building the index.

If llama-server reports model name is missing from the request, verify that you are using the current TGAIC HTML and bridge versions together.

29. Repository and project documentation

Repository file convention: keep the active browser application in the repository as tgaic-ai-coder.html. Versioned working copies such as tgaic-ai-coder-v0034.html are useful during development, while the versionless file is the stable file users should download and run locally.

Use GitHub / Docs ↗ directly beneath the TGAIC branding at the top of the application, or GitHub / README ↗ in the footer, to open the public TGAIC repository. The repository contains the README, source, setup instructions, release history, and related project resources.

30. Inspect RAG sources for every answer

When an answer used RAG, expand RAG Sources Used directly beneath the model response. It shows the exact source file, approximate line range, chunk token count, retrieval score, why the chunk was selected, and the raw reference text actually sent to the model.

This makes it easy to distinguish retrieval failure (wrong source/chunk selected) from generation failure (the right evidence was supplied but the model answered poorly).

31. Exact filename and code-aware ranking

If a question explicitly names an indexed file, that file now receives a strong file-level boost before chunks are ranked. Inside the candidate chunks, the bridge also applies lightweight code-intent boosts for imports, package declarations, exceptions, methods/functions/procedures, SQL, parameters, JDBC/database references, and class/interface/enum declarations.

For example, What imports does GentexFindFilesCp.java use? strongly favors that Java file and then boosts chunks containing import statements.
